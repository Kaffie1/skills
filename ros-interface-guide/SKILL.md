# ros-interface-guide

这个 skill 用于把现有 ROS 工程整理成一份对外可读、可调用的接口说明文档。

目标不是解释内部架构，而是帮助外部联调人员快速回答这些问题：

- 有哪些 topic 和 service
- 每个接口的消息类型是什么
- 这个接口怎么调用
- CLI 和 Python 示例怎么写
- 消息体 / 请求响应长什么样
- 常用启动和验证命令是什么

## 适用场景

在这些情况下使用本 skill：

- 用户要求“整理 ROS 接口说明”“输出使用指南”“梳理 topic/service”
- 用户希望给客户、测试、联调同学提供一份外部使用文档
- 用户要求把现有代码里的 ROS 接口定义、示例和命令写成 Markdown

如果用户主要是要新增功能、修 bug、做架构修改，不要用这个 skill，优先走对应的编码工作流。

## 工作方式

先做最小澄清，然后直接落文档。

默认按下面顺序执行：

1. 确认目标范围
- 需要整理哪个包、模块或机器人型号
- 输出到哪个文件
- 是新建文档还是更新现有文档

2. 读取现有代码和配置
- 优先看 `README.md`、`package.xml`、`launch/`、`msg/`、`srv/`
- 再看节点入口、publisher、subscriber、service server/client、参数读取位置
- 如果仓库里已经有接口说明文档，先沿用原风格，不另起一套

3. 提取接口信息
- Topic：话题名、消息类型、说明、CLI 示例、Python 示例、消息内容
- Service：服务名、服务类型、说明、CLI 示例、Python 示例、请求内容、响应内容
- 参数：参数名、默认值、说明
- 常用命令：启动、查看、调用、验证

4. 生成对外文档
- 面向外部人员，默认保持简洁
- 重点写“怎么用”，不要展开内部实现细节
- 如果用户没有特别要求，不写源码路径
- 如果用户没有特别要求，文档开头只保留一段简短引言，不额外添加“适用节点”“说明”“背景”之类的前置小节

## 输出要求

默认输出风格必须满足这些规则：

1. 文档面向外部人员
- 优先让人快速找到接口和调用方式
- 不默认写内部架构说明

2. 总览先行
- 先给 Topic 总览表
- 再给 Service 总览表
- 再给参数和常用命令

3. 每个接口都要有详细说明
- Topic 需要有：
  - `消息类型`
  - `接口类型：topic`
  - `说明`
  - `消息内容`
  - `CLI 示例`
  - `Python 示例`
- Service 需要有：
  - `消息类型`
  - `接口类型：service`
  - `说明`
  - `请求内容`
  - `响应内容`
  - `CLI 示例`
  - `Python 示例`

4. 消息内容必须写成代码块
- 用接近 `.msg` / `.srv` 原定义的形式
- 默认补字段注释，优先直接沿用 `.msg` / `.srv` 里的注释；如果原定义缺注释，可结合代码语义补最小必要说明
- 不要只写业务摘要

5. 示例必须可执行
- CLI 示例优先用 `rostopic pub`、`rostopic echo`、`rosservice call`
- Python 示例优先用 `rospy`
- 示例要和真实接口名、真实类型保持一致

6. 命令要尊重项目现状
- 如果项目实际通过 `roslaunch` 启动，就写 `roslaunch`
- 如果项目文档已经约定 Docker、supervisor、容器名或工作目录，按现有约定写
- 不要自己发明一套与仓库不一致的命令

7. 修改已有文档时要保持风格一致
- 用户已经定下标题、编号、表格字段或章节顺序时，不要随意重构
- 只改用户要求的部分，避免把整个文档洗一遍

## 推荐结构

优先使用 [assets/interface-guide-template.md](assets/interface-guide-template.md) 作为起稿模板。

如果用户已有现成文档，就以现有文档为准，只把这个模板当检查清单使用。

## 提取规则

整理接口时按这些规则执行：

- 只写代码里真实存在的接口，不猜
- 一个接口若是型号专属，要在说明里写清楚适用范围
- 自定义 `msg/srv` 优先从定义文件提取
- 标准消息若字段很多，默认保留主要字段；如果用户明确要求完整结构，就按真实定义展开
- 如果当前环境能运行 `rosmsg show` / `rossrv show`，可优先用它核对；否则从源码定义文件提取
- 如果消息或服务定义文件里存在但节点没有真实注册，不要写进对外接口清单

## 质量检查

交付前至少自查这些点：

- 话题名和服务名是否与代码一致
- 消息类型是否与代码一致
- 代码块里的字段注释是否清楚且没有脱离真实定义
- CLI 示例是否与真实接口类型匹配
- Python 示例是否导入了正确消息或服务类型
- 章节编号是否连续
- 总览表和详细说明是否一致
- 用户特别要求的字段名、标题名、路径名是否保留

## 默认行为

如果用户只说“写接口说明”，默认这样处理：

- 生成 Markdown 文档
- 风格面向外部联调人员
- 同时包含 Topic、Service、参数、常用命令
- 每个接口都包含 CLI 和 Python 示例
- 消息内容使用带字段注释的代码块展示
- 开头默认只写一段引言，不额外扩展前置说明

如果代码里接口很多，而用户没有要求全量展开，可以先交付：

- 总览
- 核心接口的详细说明

但只要用户明确要求“所有接口”，就必须全量整理。
